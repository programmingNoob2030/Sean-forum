# RECENT 排序性能测试 — Fine

## 1. 测试目的

在 Coarse 测试确定性能明显恶化区间后，对 RECENT 排序进行细粒度并发测试，定位性能开始明显退化的并发区间。

本次 Fine 测试重点观察 **P95 响应时间**，并计算相邻并发测试点之间的 P95 涨幅。

------

## 2. 测试条件

| 项目     | 配置                   |
| -------- | ---------------------- |
| 排序方式 | `RECENT`               |
| 数据规模 | 约 10000 条帖子        |
| Threads  | 10 ～ 100，每次增加 10 |
| Ramp-Up  | 10 s                   |
| Loops    | 10                     |
| 总请求数 | Threads × 10           |
| 主要指标 | P95                    |
| 辅助指标 | Avg、P99、成功率       |

## 4. 结果分析

### 4.1 低并发阶段

10 ～ 50 threads：

- P95 基本维持在 34 ～ 37 ms；
- 相邻测试点之间没有持续明显增长；
- 系统整体处于较稳定状态。

因此可以认为 **50 threads 以内尚未出现明显的性能退化**。

### 4.2 性能开始明显退化

从 60 threads 开始：

- 60 threads：P95 = 56 ms，较 50 threads 上升 55.56%；
- 70 threads：P95 = 115 ms，较 60 threads 上升 105.36%；
- 80 threads：P95 = 472 ms，较 70 threads 上升 310.43%。

P95 开始出现明显的非线性增长。

因此，本次测试认为 **RECENT 排序的性能退化开始出现在约 50 ～ 60 threads 附近**。

### 4.3 高并发阶段

80 threads 之后，P95 已经进入数百毫秒级：

- 80 threads：472 ms
- 90 threads：551 ms
- 100 threads：1010 ms

虽然部分相邻点的增长幅度存在波动，但整体趋势已经明确表现为性能持续恶化。

------

## 5. 拐点判断

综合 Fine 测试结果：

> **RECENT 排序在当前数据规模和测试环境下，约 50 ～ 60 threads 后开始出现明显性能退化。**

这里的“拐点”表示系统从相对稳定状态进入明显性能退化状态的并发区间，并不意味着存在一个绝对精确的单一线程数。

------

## 6. 后续优化对照

本次测试作为 **纯 MySQL 基准结果**，后续分别加入索引和 Redis 后，在尽可能保持测试条件一致的情况下重新测试。

重点比较：

> **性能明显退化的并发区间是否向更高的 Threads 移动。**

如果优化后需要更高的并发才能进入明显退化区，则可以说明优化提高了系统在当前测试条件下的并发承载能力。

不要求人为划分或计算“优化了几个拐点”，重点关注性能退化区域的整体移动。
