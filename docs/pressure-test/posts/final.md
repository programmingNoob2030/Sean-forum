# `/posts` 接口性能测试与优化报告

## 1. 测试目的

本次针对论坛首页帖子列表接口 `/posts` 进行性能测试，主要验证不同排序方式在并发访问场景下的性能表现，并通过数据库索引与 Redis 缓存两种优化手段进行对比测试。

接口支持以下主要排序方式：

- `RECENT`：按帖子发布时间排序
- `POPULAR`：按帖子点赞数排序
- `COMMENTS`：按帖子评论数排序
- `HOT`：基于浏览、点赞、评论等数据计算综合热度后排序

测试重点关注 **P95 响应时间、平均响应时间、最大响应时间以及请求成功率**，并根据 P95 随并发线程数的变化情况判断接口是否进入明显的性能退化区间。

------

## 2. 测试环境

### 2.1 测试工具

- Apache JMeter 5.6.3
- 非 GUI 模式执行
- 每个并发档位执行 10 次请求循环
- Ramp-Up：10 秒

### 2.2 测试数据规模

当前数据库中的主要数据规模约为：

| 数据表         | 数据量  |
| -------------- | ------- |
| posts          | 10,005  |
| browse_records | 100,117 |
| comments       | 50,003  |

### 2.3 测试接口

```text
GET /posts
```

根据不同排序参数分别测试：

```text
sort=RECENT
sort=POPULAR
sort=COMMENTS
sort=HOT
```

------

# 3. 测试方法

本次测试并非直接进行优化，而是按照：

```text
原始性能测试
      ↓
定位性能退化区间
      ↓
数据库索引优化
      ↓
验证索引优化效果
      ↓
Redis 缓存优化
      ↓
验证缓存优化效果
```

的流程进行。

其中，`RECENT`、`POPULAR` 和 `COMMENTS` 的原始性能相对稳定，因此按照：

```text
pure/coarse
    ↓
pure/fine
    ↓
indexed/coarse
    ↓
indexed/fine
    ↓
cached/fine
```

进行测试。

HOT 排序在较低并发下便已经出现明显性能压力，因此没有单独构造完整的 indexed coarse/fine 测试，而是直接围绕原始测试发现的性能退化区间进行 Redis 缓存验证：

```text
pure/fine
    ↓
cached/fine
```

------

# 4. 数据库索引优化

## 4.1 优化内容

针对普通排序方式，在 `posts` 表中分别增加以下单列 BTREE 索引：

```sql
idx_posts_create_time
idx_posts_like_count
idx_posts_comment_count
```

分别对应：

```text
RECENT    → create_time
POPULAR   → like_count
COMMENTS  → comment_count
```

索引均为普通 BTREE 索引。

------

## 4.2 索引优化验证

通过 `EXPLAIN ANALYZE` 对优化前后的 SQL 执行计划进行对比。

测试结果显示，增加单列索引后，相关 SQL 的主要执行计划没有发生明显变化，仍然表现为：

```text
Table scan
    ↓
Join
    ↓
Temporary table
    ↓
Sort
```

在当前约 10,000 条帖子数据规模以及现有 SQL 查询结构下，单列排序索引没有改变主要执行路径。

因此，本次测试没有将索引优化描述为必然有效，而是通过 JMeter 实际测试进一步验证其性能影响。

------

# 5. RECENT 排序性能测试

## 5.1 Pure / Coarse

首先通过较大的线程间隔进行测试，用于确定 RECENT 排序接口的大致性能退化区间。

测试结果表明，接口在低并发下能够维持较低延迟，随着并发继续增加，P95 开始明显增长。

根据 coarse 测试结果确定后续 fine 测试范围。

------

## 5.2 Pure / Fine

在 coarse 测试确定的性能变化区间内进一步缩小线程间隔，对性能退化位置进行细化。

通过 P95 的变化观察接口在不同并发水平下的响应情况，并确定原始性能的主要退化区间。

------

## 5.3 Indexed / Coarse

在加入 `create_time` 索引后，重新测试原始性能退化区间附近的并发水平。

测试用于验证：

- 索引是否降低 P95；
- 索引是否降低平均响应时间；
- 性能退化区间是否发生变化。

测试结果显示，在当前数据规模和 SQL 执行计划下，索引优化带来的性能改善较为有限。

------

## 5.4 Indexed / Fine

进一步围绕索引优化后的性能变化区间进行细化测试。

测试结果表明，RECENT 排序接口在当前测试环境下仍存在明显的并发性能退化现象，因此继续通过 Redis 缓存验证高并发场景下的性能改善效果。

------

## 5.5 Cached / Fine

在原有性能退化区间内直接进行 Redis 缓存测试。

缓存采用 Cache-Aside 策略，TTL 设置为 10 秒。

测试结果表明，缓存命中后接口 P95 保持在较低水平，在原本出现明显性能退化的并发区间内未再出现相同程度的延迟增长。

------

# 6. POPULAR 排序性能测试

## 6.1 Pure / Coarse

POPULAR 排序在原始测试中随着并发增加出现明显的 P95 上升。

其中高并发区间出现较明显的性能退化，因此进一步缩小测试范围进行 fine 测试。

# 8. HOT 排序性能测试

## 8.1 Pure / Fine

HOT 排序与其他排序方式存在明显差异。

由于 HOT 查询涉及浏览、评论等数据的统计以及窗口函数、临时表和最终排序等计算，其原始单次查询执行成本明显高于普通排序。

在较低并发下，接口便已经出现明显的响应延迟。

本次重点围绕 5～10 threads 区间进行测试。

原始测试结果：

| Threads | P95 (ms) |
| ------- | -------- |
| 5       | 812      |
| 6       | 1231     |
| 7       | 1546     |
| 8       | 1766     |
| 9       | 2138     |
| 10      | 2345     |

从 4 → 5 threads 开始，P95 出现明显跃升；5 → 6 threads 后进一步突破 1 秒，并且后续线程数继续增加时，响应延迟持续升高。

因此：

> **HOT 排序在约 5 threads 附近开始进入明显的性能退化区间，6 threads 以后已经表现出较明显的并发承载压力。**

这里的 5 threads 并不是系统绝对容量上限，而是本次测试条件下观察到的性能明显恶化起点。

由于 HOT 在原始测试阶段便已经表现出较低并发下的明显性能压力，因此没有单独构造完整的 indexed coarse/fine 测试，而是直接针对该性能退化区间进行 Redis 缓存验证。

------

因此，在本次测试范围内，Redis 缓存明显改善了 HOT 排序接口在原始性能退化区间内的响应延迟。

# 9. `/posts` 整体测试结果

综合四种排序方式，可以得到以下性能特征：

| 排序方式 | 原始性能特征                       | 索引优化                | Redis 缓存               |
| -------- | ---------------------------------- | ----------------------- | ------------------------ |
| RECENT   | 中高并发后出现性能退化             | 改善有限                | 明显降低缓存命中场景延迟 |
| POPULAR  | 约 74 threads 附近进入明显退化区间 | 仍存在高并发压力        | P95 稳定在 6～7 ms       |
| COMMENTS | 约 72 threads 附近进入明显退化区间 | 仍存在明显退化          | P95 稳定在 5～6 ms       |
| HOT      | 约 5 threads 即出现明显退化        | 未进行完整 indexed 验证 | P95 稳定在 5～13 ms      |

可以看出，不同排序方式的性能瓶颈并不完全相同。

普通排序接口在当前数据规模下，单列排序索引没有明显改变主要 SQL 执行计划，因此索引带来的性能改善较为有限。

而 HOT 排序由于涉及较复杂的数据统计与计算，在较低并发下便已经产生明显的响应延迟，因此其性能瓶颈更加突出。

# 10. Redis 缓存优化效果

本次 Redis 优化采用 Cache-Aside 策略。

基本流程：

```text
请求 /posts
    ↓
查询 Redis
    ↓
缓存命中 ─────→ 返回缓存数据
    │
    └─ 缓存未命中
            ↓
        查询 MySQL
            ↓
        写入 Redis
            ↓
        返回数据
```

缓存有效期设置为 **10 秒**。

本次测试主要验证缓存命中场景，因此测试结果反映的是 Redis 直接返回缓存数据时的性能表现。

从 HOT、POPULAR 和 COMMENTS 的测试结果来看，在原本已经出现明显性能退化的并发区间内，Redis 缓存均能够将 P95 降低至个位数或十几毫秒范围，并且测试请求均保持 100% 成功。

因此，在本次测试环境与数据规模下，Redis 缓存能够有效减少高频帖子列表查询对 MySQL 的重复访问，并显著降低缓存命中场景下的接口响应延迟。

------

# 11. 最终结论

本次针对 `/posts` 接口的性能测试表明，不同排序方式具有明显不同的性能特征。

对于 `RECENT`、`POPULAR` 和 `COMMENTS` 等普通排序方式，增加单列 BTREE 索引后，SQL 执行计划没有发生明显变化，在当前数据规模下性能提升有限。因此，并非所有 `ORDER BY` 场景增加索引都能够获得明显收益，实际效果需要结合执行计划和压测结果判断。

对于 HOT 排序，由于其 SQL 涉及多表统计、窗口函数、临时表以及最终排序等计算，在较低并发下便出现明显的性能退化，约 5 threads 开始进入明显性能压力区间。

在 Redis 缓存命中场景下，原本出现明显性能退化的测试区间均恢复至较低延迟水平：

- POPULAR：P95 约 **6～7 ms**
- COMMENTS：P95 约 **5～6 ms**
- HOT：P95 约 **5～13 ms**

并且各组测试请求成功率均保持 **100%**。

因此，本次实验最终验证了两个结论：

1. **数据库索引优化并非必然有效，需要结合 SQL 执行计划和实际压测结果判断优化收益。**
2. **对于高频访问且允许短时间数据延迟的帖子列表接口，Redis Cache-Aside 缓存能够显著降低缓存命中场景下的响应延迟，并缓解数据库重复查询压力。**

本次测试中的性能拐点均表示**当前测试环境、数据规模和测试条件下观察到的性能退化区间**，不应直接解释为系统的绝对并发容量上限。
