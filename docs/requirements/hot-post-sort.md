# Hot Post Sort 需求文档

## 1. 背景

当前论坛项目已经具备帖子发布、帖子列表、分页查询、点赞/点踩、评论和浏览记录能力。`/posts` 接口也已经支持多种排序入口，包括最新、最受欢迎、评论数和最热门。

项目此前对 `/posts` 接口进行过 JMeter 压测，发现高并发场景下该接口存在明显性能压力。后续计划可能使用 Redis 对高频访问数据进行缓存，但在引入缓存前，需要先明确并完善 `/posts` 本身的业务排序逻辑。

本 Feature 的目标是在现有 `/posts` 接口中补充一个简单、合理、可解释、可维护的“热门帖子排序”能力。

## 2. 功能目标

1. 为 `/posts` 接口增加可用的热门排序能力。
2. 热门排序综合考虑近期浏览、净点赞、顶级评论和发布时间。
3. 通过归一化处理不同数量级的指标，避免单个原始指标因数值过大压倒其他指标。
4. 通过时间因子提高新帖曝光机会，降低老帖仅凭历史互动长期占据热门前列的概率。
5. 保持现有 `/posts` 分页查询、社区筛选、用户评分状态返回等能力不被破坏。
6. 不引入 Redis 缓存、推荐系统、机器学习、大数据或 Elasticsearch 等复杂方案。

## 3. 功能范围

### 3.1 本期范围

- `/posts` 接口支持 `sort=HOT` 时返回热门排序结果。
- 热门排序面向当前 `/posts` 的帖子列表查询场景。
- 支持与现有分页参数共同使用。
- 支持与现有 `boardId` 社区筛选参数共同使用。
- 热门度由以下四项指标组成：
  - 近 24 小时不同用户浏览人数，权重 `0.10`
  - 净点赞数，权重 `0.25`
  - 顶级评论数量，权重 `0.25`
  - 时间因子，权重 `0.40`
- 数量型指标需要进行压缩和归一化后再参与加权。
- 净点赞数可能为负数，需要有明确处理规则。

### 3.2 不在本期范围

- Redis 缓存。
- 修改 `browse_records` 表结构。
- 修改其他数据库表结构。
- 新增推荐系统或个性化推荐。
- 新增搜索引擎排序。
- 修改帖子详情浏览记录写入机制。
- 修改点赞/点踩业务流程。
- 修改评论发布、删除或恢复业务流程。
- 修改前端页面交互，除非后续开发发现当前前端缺少调用 `sort=HOT` 的必要入口。
- 基于 JMeter 的性能优化实施。

## 4. 用户行为

### 4.1 查看全站热门帖子

用户进入帖子列表页，选择“最热门”排序后，系统应按热门度从高到低返回帖子。热门度越高的帖子越靠前。

### 4.2 查看社区内热门帖子

当用户在指定社区范围内查询帖子，并选择热门排序时，系统应只在该社区的候选帖子中计算和排序热门度。

### 4.3 分页浏览热门帖子

用户切换热门排序后继续使用分页功能。分页结果应基于全量候选帖子的热门度排序，而不是仅对当前页帖子进行局部排序。

### 4.4 未登录用户浏览热门帖子

现有 `/posts` 查询支持可选认证。未登录用户也应能够按热门排序浏览帖子，但返回结果中与当前用户评分状态相关的字段可保持现有未登录行为。

## 5. 热门排序规则

热门排序分数由四项指标加权得到：

| 指标 | 权重 |
| --- | --- |
| 近 24 小时不同用户浏览人数 | 0.10 |
| 净点赞数 | 0.25 |
| 顶级评论数量 | 0.25 |
| 时间因子 | 0.40 |

权重总和为 `1.00`。

最终排序规则：

1. 按热门度分数从高到低排序。
2. 当热门度分数相同时，较新的帖子优先。
3. 当发布时间也相同时，使用帖子 ID 保持稳定排序。

## 6. 四项指标定义

### 6.1 近 24 小时不同用户浏览人数

定义：最近 24 小时内浏览过该帖子的不同用户数量。

规则：

- 数据来源为现有 `browse_records`。
- 只统计帖子浏览记录。
- 同一个用户在 24 小时内多次浏览同一个帖子，只计算为 `1` 个用户。
- 不统计超过 24 小时的浏览记录。

### 6.2 净点赞数

定义：

```text
净点赞数 = 点赞数 - 点踩数
```

规则：

- 正向互动和负向互动相互抵消。
- 净点赞数可以为正数、零或负数。
- 净点赞数越高，说明帖子获得的正向反馈越强。
- 净点赞数为负数时，应降低该帖子的热门度。

### 6.3 顶级评论数量

定义：直接评论在帖子下的评论数量。

规则：

- 只统计直接属于帖子的顶级评论。
- 不统计评论下面的回复。
- 已删除评论不应计入顶级评论数量。
- 顶级评论数量越高，说明帖子引发的讨论越强。

### 6.4 时间因子

定义：根据帖子发布时间计算的时间衰减分。

规则：

- 新帖子时间分更高。
- 随着帖子年龄增加，时间分逐渐降低。
- 时间因子用于避免老帖子只凭历史互动数据长期占据热门排序前列。
- 时间衰减方案应简单、合理、容易解释。

## 7. 数据统计范围

1. 帖子候选范围应与当前 `/posts` 查询范围保持一致。
2. 当传入 `boardId` 时，只在该社区范围内计算热门度。
3. 未传入 `boardId` 时，在全站帖子范围内计算热门度。
4. 浏览人数只统计最近 24 小时内的帖子浏览记录。
5. 顶级评论只统计未删除的顶级评论。
6. 热门排序不要求读取 Redis 中的最近浏览缓存。

## 8. 业务约束

1. 本 Feature 不修改浏览记录写入规则。
2. 本 Feature 不修改点赞/点踩状态切换规则。
3. 本 Feature 不修改评论层级模型。
4. 本 Feature 不修改数据库结构。
5. 本 Feature 不引入 Redis 缓存。
6. 本 Feature 不改变 `/posts` 的统一返回格式。
7. 本 Feature 不影响帖子详情、帖子发布、删除、恢复、点赞、点踩、评论和消息通知等已有流程。
8. 热门排序应基于可解释的公式，便于面试说明和后续维护。

## 9. 边界情况

1. 没有任何浏览、点赞或评论的帖子，仍应能得到合理热门度分数。
2. 净点赞数为负数的帖子，热门度应低于相同条件下净点赞为零或正数的帖子。
3. 新帖即使互动较少，也应通过时间因子获得一定排序机会。
4. 老帖即使历史互动较多，也会因为时间衰减降低排名。
5. 没有 24 小时浏览记录时，浏览指标不应导致计算异常。
6. 没有评论时，评论指标不应导致计算异常。
7. 所有帖子互动指标都为零时，系统仍应返回稳定排序结果。
8. 分页参数非法或缺失时，继续遵循当前 `/posts` 的默认分页行为。

## 10. 验收标准

- [ ] `/posts?sort=HOT` 能够返回按热门度排序的帖子列表。
- [ ] `/posts?sort=HOT&pageNum=1&pageSize=10` 返回的是全量候选帖子按热门度排序后的第一页，而不是当前页内重新排序。
- [ ] `/posts?sort=HOT&boardId={id}` 只在指定社区候选帖子中计算热门度和排序。
- [ ] 最近 24 小时内同一用户多次浏览同一帖子，只计为一个浏览用户。
- [ ] 超过 24 小时的浏览记录不参与浏览人数指标。
- [ ] 净点赞数为负数时不会导致计算错误，并会降低帖子热门度。
- [ ] 顶级评论数量只统计直接属于帖子的未删除评论，不统计回复评论。
- [ ] 新帖子在其他指标相近时优先于老帖子。
- [ ] 没有浏览、点赞和评论的帖子仍可正常参与排序。
- [ ] `RECENT`、`POPULAR`、`COMMENTS` 等已有排序行为不因本 Feature 失效。
- [ ] `/posts` 的返回结构继续使用现有 `PageResult<PostVO>`。
- [ ] 未登录访问 `/posts?sort=HOT` 时不因用户 ID 为空导致异常。
